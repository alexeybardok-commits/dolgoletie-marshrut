# Бизнес-правила регулярных групп — FE-008–FE-013

Публичные функции и производные типы экспортируются через `index.ts`.
Вход — `getCatalogData().data` из FE-006/007. Схемы, enum, ссылки, цены и
Schedule уже должны быть проверены нормализатором. Эти функции не заменяют
runtime-валидацию произвольного JSON и не изменяют входные объекты.

| Задача | Функции и правила |
| --- | --- |
| FE-008 | `calculateMonthlyCost`, `calculateGroupCosts`, `calculateCatalogCosts`: free=0, perLesson=priceAmount×число валидных сессий группы×4, monthly=priceAmount. Производная стоимость всегда пересчитывается; входной кеш не читается. |
| FE-009 | `filterCatalog`: только active/openNow, AND между группами, OR внутри directionIds/areaIds/weekdays, район не исключает online, hybrid соответствует обеим форматным предпочтениям. |
| FE-010 | `orderCatalog`: стабильное разделение уже отфильтрованной выдачи на локальные offline/hybrid, затем online. Районы равноприоритетны; исходный порядок должен быть порядком нормализованного JSON. Без района возвращается копия в исходном порядке. |
| FE-011 | `findTimeConflicts`: все пары валидных недельных сессий на одном weekday, строгое пересечение, касание не конфликтует. Включает повторяющиеся сессии и все форматы. |
| FE-012 | `findRoadWarnings`: только offline/offline, разные venueId, один weekday, непересекающиеся интервалы, gap 0–29 минут. При конфликте эта пара не получает road warning. |
| FE-013 | `aggregatePlan`: уникальные существующие ID без лимита, все Schedule-сессии, ориентировочная месячная сумма, time/road/budget warnings. Неизвестные ID игнорируются; предупреждения не удаляют группы и не запрещают выбор. |

`CatalogFilters` — состояние запроса, производное от существующих типов,
не новая сущность данных. `timeFrom` и `timeTo` — nullable-границы HH:mm,
сравниваемые включительно с startTime одной сессии. Дни и время должны
совпасть в одной сессии; отдельно заданные дни или время работают независимо.
`TIME_PERIODS`: morning 08:00–11:59, day 12:00–16:59, evening 17:00–21:00.
Пустые массивы и null-границы не ограничивают выдачу.

`areaIds` использует значения `Venue.area`: отдельной сущности Area в baseline
нет. Направления совпадают по явно связанным ID, без добавленного наследования
фильтра по дереву направлений. Бюджет каталога — 0/2000/5000/10000/null.
Бюджет плана остаётся number|null согласно ActivityPlan: строгое total > budget
даёт предупреждение, null не ограничивает и не предупреждает.

`PlanSummary` — вычисляемый результат, не второй формат хранения. Сессии
упорядочены по ISO weekday и времени начала. Список выбранных групп сохраняет
порядок уникальных входных ID. Результаты конфликтов и дороги содержат обе
группы и сессии с weekday/start/end для будущего отображения. Дорожный порог
фиксирован и не является расчётом реального времени в пути.

Пример использования будущими потребителями: получить нормализованные данные,
затем вызвать `calculateCatalogCosts(data)` для полноценного ActivityGroup;
`filterCatalog(data, filters)` и `orderCatalog(filtered, data.venues, filters.areaIds)`
для выдачи; `aggregatePlan({ activityIds, monthlyBudget }, data)` для сводки.
Catalog подключён к нормализатору, filterCatalog и orderCatalog в FE-016–022.
Help Select преобразуется в обычные фильтры через preferencesToFilters.
Legacy-JSON и legacyModel сохранены отдельно. Из новых фильтров сохраняется
только бюджет в составе ActivityPlan; остальные фильтры остаются временными.
FE-026 использует `addActivityId` для уникальных ID регулярных групп и
пересчитывает aggregatePlan в памяти приложения. Повторное добавление
не удаляет группу; предупреждения не блокируют выбор.

`npm.cmd test` — Vitest без watch; `npm.cmd run check` — прежние 41 проверка
нормализации и затем Vitest. Тесты проверяют бизнес-правила этого этапа,
а не соответствие существующего legacy-интерфейса baseline. Detail и Added
реализованы в FE-025–027. My Plan, недельное представление, вывод готовых
предупреждений, Undo и сохранение бюджета реализованы в FE-028–032.
Расчётные правила не дублируются в компонентах.

## FE-023 — локальный текстовый поиск

`filterCatalog` применяет поиск через AND к прежним условиям, перед прежним
стабильным `orderCatalog`. Поля поиска: ActivityGroup.title/description,
Direction.name, Instructor.name, Organizer.name, Venue.name/address/area/landmark.
Для pure online физические поля Venue не участвуют даже при переданном venueId.
Отсутствующие optional-поля не подменяются текстом «Информация отсутствует.».

Запрос — обычный текст без regex, HTML, API или ранжирования. Регистр,
ё/е, Unicode NFKC и пробельные/control-символы нормализуются. Все слова
запроса должны встретиться в доступных полях группы; это поиск подстрок,
без морфологии, исправления опечаток и специального синтаксиса кавычек.
Пустые/пробельные и нестроковые значения не ограничивают выдачу. Остальные
строки, включая похожие на код, ищутся буквально и не исполняются.

## FE-024 — дополнительные фильтры

`skillLevels` и `physicalLoads` используют только фактические значения
skillLevel/physicalLoad нормализованных групп: OR внутри набора и AND между
ними и основными фильтрами. В исходной доменной модели оба поля обязательны;
повреждённые записи без них исключает существующий нормализатор.

`elevator` и `stepFreeEntrance` имеют условия any/yes/no/unknown.
yes совпадает только с true, no — только с false, unknown — с null/отсутствием.
Для pure online оба физических условия неприменимы и не исключают группу.
Hybrid проверяется по физической площадке. Фильтра enrollmentStatus нет;
основная выдача по-прежнему ограничена active + openNow.

Каталог показывает удаляемые условия и полный сброс. Эти параметры и query
живут только в `PlanSession.filters`, без изменений контракта ActivityPlan.
При неизменном бюджете ссылка на plan остаётся той же, поэтому временные
условия не запускают запись storage. Полный сброс по прежнему правилу также
сбрасывает общий бюджет в null, сохраняя выбранные группы.

В текущем demo-наборе только одно значение уровня и одно нагрузки; UI не
добавляет вымышленных характеристик. Известных ориентиров нет — все landmark
null/отсутствуют. Поиск по заполненному landmark и разные уровни/нагрузки
проверены нормализованными тестовыми фикстурами без изменения рабочих JSON.
