## Как читать результаты

- PASS — проверка действительно выполнена указанным способом и дала ожидаемый результат.
- FAIL — выполненная проверка выявила отклонение.
- NOT VERIFIED — проверка не выполнена; это не доказанный дефект и не PASS.
- Ручное прохождение: человек взаимодействует с интерфейсом, оценивает результат
  и фиксирует фактические наблюдения. Playwright, SSR, unit-тест и чтение кода
  не называются ручной проверкой, даже когда они подтверждают тот же сценарий.

браузерная матрица и журнал — в [MANUAL_ACCEPTANCE_GUIDE.md](MANUAL_ACCEPTANCE_GUIDE.md).

## FE-022/023 — отзывчивость production-каталога

Воспроизведение из `app/` после сборки:

```powershell
npm.cmd run build
node scripts/measure-catalog.mjs
```

Скрипт запускает preview на свободном порту 4191, установленный Edge и закрывает
их после проверки. Логи JSON выводятся в stdout; постоянный отчёт с секретами
или пользовательскими данными не создаётся. При необходимости локальный JSON
можно сохранить в игнорируемый `app/test-results/`, не добавляя в Git.

Методика: 13 raw-групп / 15 сессий, 7 групп в основной выдаче; production build,
headless Edge, viewport 1440/390×900, без CPU/network throttling. Одна полная
последовательность — прогрев, затем 10 повторов восьми действий на каждой ширине.
Начало отсчёта — capture-событие click для checkbox/кнопки, change для бюджета,
input для поиска. Для checkbox именно click предшествует обработчику React;
позднее событие change могло бы занизить время. Конец DOM-метрики — точный
ожидаемый список заголовков карточек и статус количества. Затем фиксируются
два requestAnimationFrame как возможность отрисовки. Доставка действия
Playwright, прокрутка, начальная загрузка, физическая задержка монитора и
задержка отдельного нажатия клавиши не входят в измерение.

Это отдельные браузерные часы `performance.now()`, а не длительность E2E-теста.
PerformanceObserver записывает Long Tasks в измерительном окне; отсутствие
таких записей не является полной оценкой всех возможных зависаний на другом ПК.
10-секундный watchdog нужен для обнаружения сломанного измерения, а не задаёт
допустимый UX-порог. Малый n=10 и nearest-rank p95 означают, что p95 равен
максимуму в каждой группе. INP/Lighthouse, реальные телефоны и большие каталоги
не проверяются. Числовой обязательный SLA в ТЗ не задан.
